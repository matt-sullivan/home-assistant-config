- `agent-srv`'s `docker` CLI is backed by a rootless Podman engine, with SELinux enforcing. A plain bind-mount (`./data/config:/config`) fails during the image's `init-adduser` step with `chown: changing ownership of '/config': Permission denied`. This looked at first like a UID-mapping issue, but adding only the UID-remap flag (`:U`) still gave `Permission denied` even to a root shell inside the container - the real cause was SELinux: the host directory carried the `user_home_t` context, not `container_file_t`. Fix: mount with both `:U,Z` (`./data/config:/config:U,Z`) - `Z` relabels the directory for exclusive container access, `U` fixes UID ownership. Worth checking whether `frigate-srv3` has the same rootless-Podman + SELinux-enforcing setup when deploying there; if it runs a real Docker daemon or has SELinux permissive/disabled, these flags are unnecessary but harmless.
- Once `:U,Z` relabels `./data/config`, it's no longer readable/writable by the host `core` user directly - editing files under it (e.g. `authorized_keys`) from the host now needs `docker exec`/`docker cp`, not a plain host-side `cat`/editor.
- `esphome compile` fails with "Git not found in PATH" - PlatformIO needs `git` to fetch the ESP32 platform/toolchain packages. Added `git` to the Dockerfile's `apt-get install` line alongside `openssh-server`/`nodejs`/`npm`.
- `esphome compile` then failed again with "ensurepip is not available... apt install python3.12-venv" while PlatformIO tried to create its toolchain venv. Added `python3-venv` to the same `apt-get install` line. The imagegenius base image's own bundled Python appears trimmed of the stdlib `venv`/`ensurepip` modules, unlike a stock Ubuntu 24.04 image - worth re-checking for further missing build deps (e.g. `build-essential`/`cmake`) if a future ESP-IDF (not just Arduino framework) compile fails similarly.
- Task 3.1 (mDNS device discovery) - **resolved.** Initially found 0 devices via a Python `zeroconf` browse for `_esphomelib._tcp.local.`, despite the ESP fleet being on the same subnet as `agent-srv` and the interface having joined the mDNS multicast group. Root cause, confirmed via `sudo firewall-cmd --list-all` (read-only, passwordless sudo available on this box): `firewalld`'s active `FedoraServer` zone only permitted `cockpit dhcpv6-client ssh` - no `mdns` service, no port 5353 rule. Fixed with `sudo firewall-cmd --permanent --add-service=mdns --zone=FedoraServer && sudo firewall-cmd --reload`. Re-ran the same browse afterward and discovered all 29 real fleet devices by name. This is now recorded in `design.md`'s Migration Plan as something to check on `frigate-srv3` too. I didn't plan for the agent to make this change, and it'll need to be merged into
the IaC config, but for now it's ok.
- Task 3.3 verification used a plain file edit inside the container (`sed -i` via `docker exec`) rather than a live authenticated Claude Code session - this throwaway test container has no Anthropic credentials configured, and the property being tested (an edit under `/config` is immediately visible to `esphome`, with no sync/copy step) doesn't depend on which process made the edit, only on both reading/writing the same mounted volume.
- `agent-srv` is memory-constrained (3.8GB total, often <1GB free with other sessions/VS Code running). `docker build --load` (which routes through `buildkitd` via the `docker-container` driver, plus an export/import tarball round-trip) got OOM-killed by the harness twice during this session. `podman build` directly (native, no buildkitd, no tarball round-trip) succeeded quickly with the same Dockerfile and was noticeably lighter - prefer it on this host. A plain `esphome compile` of the ESP32 toolchain (downloading + unpacking PlatformIO's espressif32 platform, then compiling) also got OOM-killed once under load; worth checking `frigate-srv3`'s available memory before assuming this container can reliably do a fresh (uncached) ESP32 build there.
- **Rebuild after more memory/disk were made available** (retested with the flattened repo-root structure): `podman build` succeeded cleanly this time (6.2GB RAM now vs. 3.8GB before). But the container failed to start its custom services - `s6-rc-compile: fatal: unable to open /etc/s6-overlay/s6-rc.d/sshd/run: Permission denied`, with s6-overlay's own banner warning "You are running this container as a non-root user: ... custom services ... will be disabled". Cause: `~/.ssh/../.config/containers/containers.conf` on `agent-srv` now has `[containers] userns = "keep-id"` (not present earlier in this session - added at some point during the "more memory and disk" changes, by Matt or something he ran), which makes rootless Podman run every container's init process as the host's own UID instead of root-in-namespace, so s6-overlay can't set up custom longrun services at all. Per the new "Servers" policy in `AGENTS.md`, did not touch that host-level containers.conf. Fixed instead at the container level - added `userns_mode: host` to `docker/docker-compose.yml`, which overrides `keep-id` back to normal rootless behavior for just this container. Confirmed working after the fix: sshd, custom services, and everything else all started correctly.
- **Base image switch to `baseimage-ubuntu` + self-installed ESPHome (see design.md's updated base-image Decision)**: initially wrote the ESPHome dashboard's s6-rc service mimicking imagegenius's own `s6-notifyoncheck -d -n 300 -w 1000 -c "nc -z 127.0.0.1 6052" s6-setuidgid abc esphome dashboard /config` wrapper. It failed on this base with `s6-notifyoncheck: fatal: unable to read ./notification-fd: No such file or directory`, repeating forever and never actually starting the wrapped command - `s6-notifyoncheck` needs an explicit `notification-fd` declaration wired into s6-rc that imagegenius's build has and this one-off service definition didn't. Not essential (it's a readiness-signal wrapper, not required for the process to run), so dropped it entirely - the service just `exec`s `esphome-device-builder /config` directly now, same pattern already proven for sshd.

- **2026-09-22, `:U` mount flag dropped - supersedes the "found by testing an actual restart" fix in the entries above and in `design.md`'s superseded text.** The recursive-`chown` fix (this file's earlier entries, `design.md`) worked but left `:U` and our own `chown -R` fighting each other on every restart. Delegated a research pass to another agent (asked to read Podman's actual source and search for best practice, not just theorize) after repeatedly hitting new chown/bind-mount theories in this same area. Findings, cited to `libpod/container_internal_common.go`: `:U`'s "initial creation" doc comment is misleading - it does a cheap top-level ownership check on every start and falls through to a full recursive chown-to-container-UID (root) whenever that check fails, which it always will once a prior run has legitimately re-owned the volume to `abc`. Also confirmed (separately) that kernel ID-mapped mounts (`idmap`) are rootful-Podman-only, not an option here. Per this project's own working practice (verify advice against the real system, don't just accept a report), independently re-tested before committing to the fix: a virgin host-`core`-owned directory mounted `:Z`-only (no `:U`) had no permission error and correct resulting ownership - so `:U`'s bootstrap role isn't needed here either, a step further than the research report's own hedged recommendation to keep a `podman unshare chown` fallback. Also re-verified full three-mount (`/config`, `/ssh`, `/home/abc`) behavior across two separate `podman restart` cycles - ownership stayed correct throughout both times. Fix shipped: all three `Volume=`/`-v` mount flags changed from `:U,Z` to `:Z` only; `chown -R` in `docker/Dockerfile`'s `sshd/run` is unchanged and is now the sole ownership mechanism.
- **2026-09-22, `UserNS=host` dropped in favor of `keep-id`+`User=0` - supersedes the `:U`-drop entry above.** The `:U`-drop fix (previous entry) was internally correct but left the host user (`core`) unable to read or write `/config`/`/ssh`/`/home/abc` at all once the container had started once - `UserNS=host`'s default rootless mapping sends container UID 1000 (`abc`) to a subuid-range host UID (`525287`), not `core`. Caught by re-checking against the original reason these are bind mounts (host-editable files), not by a new bug. Delegated a second research pass (same practice as before: read real sources, don't theorize) specifically on `keep-id`+`--user root` as a fix. Findings: this is the documented (if informally-named) Podman answer (`containers/podman#24934`); LinuxServer.io states plainly they don't support rootless Podman at all for exactly this reason (s6-overlay's init needs root, and plain `keep-id` runs PID1 as the mapped non-root UID instead); per-volume `idmap` (considered as an alternative) is rootful-Podman-only (`containers/crun#1632`), consistent with the earlier idmap finding. Also flagged a real, previously-untested risk specific to this deployment: `containers/podman#25395` reports `UserNS=keep-id` failing with an overlay-permission error specifically when started via a Quadlet-generated systemd unit (vs. a hand-run `podman run`) - directly relevant since this project deploys exclusively via Quadlet.
  Independently verified beyond the report (per established practice - verify before trusting): confirmed `frigate-srv3` also runs `core` at UID/GID 1000 with the same `/etc/subuid`/`/etc/subgid` range as `agent-srv` (`524288:65536`), so `PUID=1000`/`PGID=1000` is valid on both hosts (this project's whole `keep-id` scheme depends on `PUID`/`PGID` matching the deploying host user's real UID - not previously stated explicitly). Confirmed `keep-id`+`User=0` fixes host-editability end-to-end: real SSH login, files created inside the container land as `core:core` on the host, direct host-side edits work, survives two `podman restart` cycles. Then specifically exercised the Quadlet/systemd risk the research report flagged: built a real Quadlet `.container` unit and cold-started it via `systemctl --user start` (not `podman run`) from fresh volumes, then `systemctl --user restart`, then a full `stop`+`start` cycle (simulates a host reboot) - all clean on Podman 5.8.4, no overlay error, correct `core:core` ownership throughout. Also confirmed `loginctl show-user core` shows `Linger=yes` already on both hosts (a prerequisite the report flagged for a rootless Podman unit to start at boot). Fix shipped: Quadlet `UserNS=keep-id`, `User=0`, mounts unchanged (`:Z` only).
